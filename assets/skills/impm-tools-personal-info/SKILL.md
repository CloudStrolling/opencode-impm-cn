# impm-tools-personal-info 技能

## 触发词
个人信息保护、个保法、PIPL、个人信息合规、个人信息保护法检查、数据采集合规、数据存储合规、数据传输合规、数据合规检查、tools-personal-info

## 何时使用
需要对当前项目进行《中华人民共和国个人信息保护法》（PIPL）合规检查，逐项核查项目在个人信息采集、传输、存储（及删除、权益保障）各环节的合法合规性，并最终在 docs 目录下输出完整检查报告时使用。可独立执行，也可在阶段4代码审核后追加执行。

## 执行角色
本技能由 技术负责人（subagent_type=tl）subagent 负责执行，执行时使用 Skill 工具加载本技能。

## 调度说明（PM/上级编排者启动本技能时必须遵守）
1. 启动方式：使用 task 工具启动 subagent，subagent_type 必须为 `tl`；禁止由 PM 或编排者自己代替执行本技能内容。
2. 提示词必传上下文（缺一不可）：项目根目录绝对路径（projectRoot）、项目英文缩写（impm_project_info 获取）、用户输入 $ARGUMENTS 原文（含用户提到的文件路径）、技能名（impm-tools-personal-info，要求 subagent 先用 Skill 工具加载本技能再执行）。
3. 完成要求：等待 subagent 返回完成结果后，核对检查报告已生成且内容完整，全部正确后才能结束。

## 关键变量定义与取值
| 变量 | 说明 | 获取方式 |
| --- | --- | --- |
| 项目中文名称 | 项目的中文名称 | 通过 impm_project_info 从 docs/project.md 读取 |
| 项目英文缩写 | 项目的英文缩写，用于拼接报告路径 | 通过 impm_project_info 从 docs/project.md 读取 |
| 检查清单与报告模板 | 个人信息保护检查清单与报告格式 | 通过 impm_template_reader 读取 TOOLS-PERSONAL-INFO-TEMPLATE.MD |

## 执行要求
1. 严格按照执行步骤中的内容和顺序依次执行：不跳过、不乱序、不并行、不合并任何步骤。
2. 本技能以只读检查为主：除写入检测报告外，不得修改任何代码、配置与其他文档。
3. 检查结果的取值只能为三种：通过、不通过、不适用；每条检查要点必须有实际证据支撑（文件路径与行号），禁止臆测或编造。
4. 不通过项必须给出具体的文件位置与问题描述，并附整改建议；不适用项须简要说明判断依据。
5. 报告中的个人信息内容一律脱敏处理，不得完整暴露真实姓名、手机号、身份证号、银行卡号等。
6. 所有文档路径必须用 {项目英文缩写} 拼接，不得臆造文件名。
7. 使用 impm_* 工具获取信息，不得编造工具返回结果。
8. 全程使用简体中文。
9. 检查清单依据《个人信息保护法》条文归纳，检查时先确认对应条文，再核对项目实现，不得脱离条文臆断。

## 执行步骤

### 步骤 1：获取项目信息与法律依据
1. 调用 impm_project_info 读取 docs/project.md，获得项目中文名称与项目英文缩写；若 docs/project.md 不存在（项目未初始化），终止本技能并提示先执行 /impm-init 完成初始化。
2. 明确本次检查的法律依据为《中华人民共和国个人信息保护法》（2021-11-01 施行），涉及的基本原则与一般规则（第 5、6、7、9 条）、采集（第 13、14、15、17、28、29 条）、传输（第 22、23、24、38、39、40、41 条）、存储与删除及权益保障（第 19、40、45、47、51、55、56、57 条）等条文。

### 步骤 2：读取检查清单与报告模板
1. 调用 impm_template_reader（templateName=TOOLS-PERSONAL-INFO-TEMPLATE.MD）读取模板全文，获得检查清单条目、检查环节划分与报告格式。

### 步骤 3：开展资料收集（只读探查）
1. 结合 docs/project.md 的项目地图与源代码目录结构，确定本次检查范围：源码目录、配置文件目录（config/、conf/、.env*）、数据库设计（DBD/SQL）、接口设计（API）、日志配置、部署环境等。
2. 确定排除目录列表（必须排除）：node_modules、.git、dist、build、vendor、__pycache__、.next、.nuxt、target、bin、obj 等构建/依赖产物目录。
3. 按后端语言/框架特征收集以下证据（适用时）：
   - 用户实体/模型定义、注册登录、表单采集逻辑 → 评估采集字段是否最小必要；
   - 数据库表结构与 SQL 脚本 → 评估存储字段、加密/脱敏情况；
   - API 接口定义与实现 → 评估传输是否走加密通道、返回是否脱敏；
   - 日志配置、埋点/统计代码 → 评估日志是否记录并冗余保留个人信息；
   - 缓存/存储服务（Redis、对象存储等）配置 → 评估敏感信息存储保护；
   - 数据处理协议/隐私政策文档 → 评估告知与同意机制（如存在即记录）。
4. 使用 Grep / Glob / Read 等工具按上述范围收集证据，只读探查，不改动任何文件。

### 步骤 4：逐项核查（按检查清单）
1. 按模板「二、个人信息保护检查清单」中的编号顺序（PIP-001~PIP-312）逐项核查，覆盖四个环节：
   - 基本原则与一般规则（PIP-001~007，对应第 5、6、7、9、51、47 条）；
   - 采集环节（PIP-101~109，对应第 13、14、15、17、28、29 条）；
   - 传输环节（PIP-201~209，对应第 22、23、24、38、39、40、41、51 条）；
   - 存储环节（PIP-301~312，对应第 19、40、45、47、51、55、56、57 条）。
2. 每一项根据收集到的证据判定「通过 / 不通过 / 不适用」：
   - **通过**：项目实现符合对应条款（记录证据位置）；
   - **不通过**：项目实现违反或未达到条款要求（记录文件路径、行号与问题描述）；
   - **不适用**：项目不存在该场景（记录判断依据，如"项目不涉及跨境传输"）。
3. 禁止跳过任何检查项；逐项后如发现有关联线索（如某接口采集了身份证号，应同时核查该字段的存储加密与传输脱敏），主动追查相关环节补齐证据。

### 步骤 5：汇总与生成检测报告
1. 统计各环节检查结果，填写「三、检查结果汇总」表，计算检查项总数与通过/不通过/不适用数量。
2. 对全部「不通过」项，填写「四、不通过项明细与整改建议」，给出风险等级（高/中/低）与整改建议。
3. 填写「五、检查结论与建议」，给出总体合规评估分级（全部通过 / 存在高风险项需立即整改 / 存在中低风险项建议改进）与整改建议。
4. 确定报告写入路径：使用 impm_version action=current 检查是否存在版本目录。若存在版本目录（如 docs/{项目英文缩写}-v{版本号}/），将报告写入该版本目录；否则写入 docs 根目录。报告文件名固定为 `{项目英文缩写}-personal-info-check.md`。
5. 使用 Write 工具将报告写入确定的路径。
6. 核对文件存在且内容完整：检查概况、四环节检查清单、结果汇总、不通过明细、结论建议齐全，统计数据前后一致。

## 交付物
- docs/{项目英文缩写}-personal-info-check.md（个人信息保护合规检查报告，含检查清单与逐项检查结果）

## 完成后提示
- 本技能全部操作完成后必须立即结束并返回调度方（报告路径、检查项总数与通过/不通过/不适用数量、高风险不通过项摘要）；严禁自行继续执行其他技能。
- 若为独立命令运行，向用户汇报报告位置、检查结果摘要，并高亮提示高风险不通过项与整改建议。
